# 처음 보는 청중을 위한 5분 발표 진행안

[README](../../README.md)의 1~6절을 순서대로 보여 줍니다. 본문은 청중 공유용이며 이 문서는 발표자 참고용입니다. 아래는 화면 전환을 포함한 **300초 배분안**으로, 실제 리허설 측정값은 아닙니다. 접힌 기술 상세는 질문이 있을 때만 엽니다.

| 시간 | 보여 줄 화면 | 전달할 한 가지 |
|---|---|---|
| 0:00~0:45 · 45초 | README 1절 | 자료가 흩어져 있어 같은 확인 작업이 반복됨 |
| 0:45~1:20 · 35초 | README 2절 | 가져오기 → 확인 → 승인 → 장부 조회 |
| 1:20~2:10 · 50초 | README 3절 | Agent는 도구를 선택하고 LangGraph는 순서를 관리 |
| 2:10~3:55 · 105초 | README 4절의 화면 4장 | 원문과 AI 결과를 비교하는 실제 사용 흐름 |
| 3:55~4:40 · 45초 | README 5절 | 무엇이 잘못됐고 어떻게 개선했는지 |
| 4:40~5:00 · 20초 | README 6절 | 구현 범위와 앞으로 검증할 것 |

## 0:00~0:45 · 먼저 업무의 불편함 설명

“지난달 단가표에 있던 제품을 이번 달에도 주문할 수 있을까요? 학교에서 식단을 준비할 때는 가격뿐 아니라 공급 중단 여부와 대체품도 확인해야 합니다. 그런데 가격은 엑셀, 중단 안내는 게시글, 원재료는 이미지에 흩어져 있습니다. 광주 초·중·고는 공개자료 설명 기준314개교입니다. 학교마다 같은 공지를 읽고 장부에 옮긴다면 반복되는 일입니다. 이 자료 정리를 돕기 위해 식품장부를 만들었습니다.”

학교 수는 2025-11-09 기준 자료 설명의 합계이고 실제 이용 학교 수가 아닙니다. 출처는 README에 남겨 두고 숫자 내역을 모두 읽지는 않습니다.

## 0:45~1:20 · 담당자가 어떻게 쓰는지 설명

“사용자는 자료를 가져오고, 정리된 정보를 원문과 비교하고, 확인한 항목을 승인합니다. 예를 들어 A제품 공급 중단과 B제품 대체 공지가 올라오면, 서비스가 그 내용을 검토할 초안으로 정리합니다. 담당자가 승인하면 장부를 갱신하고 나중에도 어느 공지 때문에 바뀌었는지 확인할 수 있습니다. 승인 전에는 확정된 식품 정보를 바꾸지 않습니다.”

이 단계에서는 DTO·스키마·DB 트랜잭션 같은 용어를 먼저 꺼내지 않습니다. 예시 공지는 실제 시연 입력과 구분합니다.

## 1:20~2:10 · AI의 역할을 쉽게 설명

“Agent는 자료를 보고 어떤 도구로 처리할지 고르는 AI입니다. 제품명과 가격 열이 이미 읽혔다면 표 정리 도구를 씁니다. 문장은 텍스트 해석 도구로, 이미지에서 읽은 글자는 이미지 해석 도구로 보냅니다. 읽기 어려운 자료는 원문 확인을 요청합니다. OCR은 이미지에서 글자를 읽는 기술이고, 읽은 값은 공통 식품 양식에 모읍니다. LangGraph는 자료 읽기부터 도구 선택·실행·검토본 생성까지 순서와 중간 저장을 관리합니다. 마지막 승인은 사람이 합니다.”

네 도구 표와 그림을 짚습니다. 함수 이름과 실제 노드 명세는 아래 접힌 ‘Agent와 LangGraph 구현 상세’에 있습니다. 질문이 없으면 펼치지 않습니다.

## 2:10~3:55 · 실제 사용 흐름 보여 주기

시작 문장: “다음은 실제 업체 단가표에서 저장된 분석 결과입니다. 원문과 비교할 수 있도록 만든 검수 화면을 보겠습니다.”

| 절대 시간 | 화면 | 말할 내용 |
|---|---|---|
| 2:10~2:30 | 검수함 | “자료를 가져오면 이 목록에서 진행 상태를 확인합니다. 준비가 되면 검수로 들어갑니다.” |
| 2:30~2:55 | 통합 표 | “원본 표 옆에 같은 제품의 정리된 정보를 연결했습니다. 표와 라벨에서 얻은 값을 함께 확인합니다.” |
| 2:55~3:30 | 라벨 검수 | “왼쪽이 원문, 오른쪽이 정리된 정보입니다. 틀린 값은 수정하고 필요 없는 항목은 제외합니다. AI가 잘못 읽을 수 있어서 이 확인 과정이 필요합니다.” |
| 3:30~3:55 | Agent 로그 | “어떤 도구를 왜 선택했고 어디까지 처리했는지 볼 수 있습니다. 자동화 결과를 담당자가 따라가며 확인할 수 있도록 했습니다.” |

화면은 검수 초안까지의 조회 기록입니다. 촬영을 위해 승인하거나 식품 DB를 변경하지 않았습니다. 후보 수와 호출 수는 발표 본문에서 길게 읽지 않고 접힌 촬영 기준과 [조회 기록](current-code-evidence.json)을 참고합니다. 이후 원재료 수정 결과가 기존 캡처에 반영된 것처럼 설명하지 않습니다. 직접 승인하는 시연이 필요하면 [별도 시연 DB 준비](demo-guide.md)를 먼저 완료합니다.

## 3:55~4:40 · 개선 경험 두 가지 선택

“첫 번째 문제는 자료를 읽고도 정보가 사라지는 것이었습니다.18행을 읽었는데 서로 다른 맛과 가격을 중복으로 합쳐8행만 남았습니다. 통합 기준을 수정해 같은 입력의18행을 보존했습니다. 두 번째는 원재료였습니다. 함량이 있는 재료만 분류해 대두유나 마늘처럼 함량이 없는 재료가 기타 속성에 남았습니다. 원재료 전용 추출값을 추가해 이 항목도 저장하도록 보완했습니다. 이 과정에서 AI 호출뿐 아니라 읽은 정보를 끝까지 보존하는 기준이 중요하다는 점을 배웠습니다.”

시간이 남으면 README5절의 라벨 응답 오류 사례를 한 문장으로 덧붙입니다. Before/After의 과거 실행과 최신 원재료 회귀 테스트는 검증 조건이 다릅니다. 원재료 수정은 실제 라벨 정확도 측정 결과로 소개하지 않습니다.

## 4:40~5:00 · 현재 범위와 다음 단계

“자료를 가져와 AI가 정리하고, 사람이 확인해 장부에 반영하는 흐름을 구현했습니다. 작은 라벨과 잘못 잡힌 항목은 더 개선해야 합니다. 앞으로 실제 자료의 정확도와 담당자의 검토 시간을 측정하려 합니다. AI가 자료를 정리하고, 사람이 확인한 정보로 장부를 갱신하는 서비스입니다.”
