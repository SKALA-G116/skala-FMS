# README와 시연 결과로 진행하는 5분 발표

## 0:00~0:45 · 배경

“광주 학교검색 공개자료의 2025년11월 기준 설명에는 초등155개, 중학교91개, 고등학교68개로 합계314개교가 있습니다. 학교 영양 업무에서는 제품 가격뿐 아니라 지금도 공급 가능한지 확인해야 합니다. 그런데 변경 공지는 업체별 게시글·이미지·엑셀에 흩어져 있습니다. 같은 공지를 학교마다 찾아 읽고 장부와 대조한다면 지역 규모의 반복 확인이 됩니다. 식품장부는 이 자료 정리를 Agent가 맡고, 담당자가 근거를 보고 승인하도록 만든 CMS입니다.”

학교 수는 공개자료 설명의 합계이며 서비스 사용자 수가 아님을 유지합니다. [출처와 범위](background-sources.md)

## 0:45~1:20 · 주요 Task

“업무는 네 단계입니다. 사이트나 파일에서 자료를 가져오고, Agent가 알맞은 도구로 정리하고, 사람이 원문과 대조한 뒤 승인하고, 식품 DB에서 이력을 관리합니다. 업체 양식이 달라도 같은 DTO를 사용하고, 없는 정보는 공란으로 둡니다. 분석 결과를 바로 사실로 저장하지 않고 사람이 검수하는 이유는 공급 상태나 알레르기처럼 잘못 반영했을 때 다시 확인해야 하는 정보가 있기 때문입니다.”

표의 네 Task를 짚고 다음 절로 이동합니다.

## 1:20~2:10 · 판단과 실행의 역할 구분

“Agent의 핵심은 자료에 맞는 도구를 선택하는 것입니다. 표의 열이 이미 읽혔다면 결정적인 매핑 도구를 쓰고, 서술은 텍스트 추출, OCR 자료는 상품 영역 추출로 넘깁니다. 부족한 자료는 검수 요청으로 남깁니다. LLM이 이 판단을 하고 LangGraph는 추출·계획·도구 실행·DB 후보 연결·검토본 생성 순서와 재개를 관리합니다. 마지막 DB 반영은 이 그래프가 임의로 수행하지 않습니다. 사용자 승인 후 서버가 근거와 버전 등을 검사해 반영합니다.”

README3절에서 네 도구 이름과 짧은 예시를 짚고, LangGraph 단계 그림의 plan·execute_tools·export를 따라갑니다. 상세 함수 표·MCP 설명은 링크된 별도 문서로 두고 본문을 전부 읽지 않습니다. OCR는 extract에서 준비한다는 점은 필요 시 짧게 보충합니다. MCP·모델별 설정은 접힌 상세 명세에 두고 본문에서 길게 설명하지 않습니다.

## 2:10~3:55 · 실제 실행 결과 공유

시작 문장: “다음은 기수집한 실제 업체 엑셀을 별도 문서로 재등록해 처리한 당시의 결과입니다. 현재 DB에는 해당 과거 작업이 없어 보관한 화면과 로그로 공유하겠습니다.”

| 절대 시간 | 조작과 말할 내용 |
|---|---|
| 2:10~2:30 | 표 필터 캡처: “50g인 원본 세 행입니다. 이름과 규격이 같아도 맛과 가격이 다릅니다.” |
| 2:30~2:55 | Agent 로그 캡처: “Agent가 표 도구를 선택했습니다. 실제4B 모델은 선택에1회 호출했고, 행별 추출 LLM은 쓰지 않았습니다.18개 검토 품목이 만들어졌습니다.6.027초는 이 작업의 시작부터 완료까지이며 수집·검수 전체 시간은 아닙니다.” |
| 2:55~3:30 | 검수 캡처: “왼쪽 원문과 오른쪽 DTO를 비교합니다. 식품명·규격·맛을 분리하고 없는 값은 공란입니다. 수정·확인·제외 후 최종 승인합니다. 이18행은 검토 대기 상태까지 촬영했고 DB에 승인하지 않았습니다.” |
| 3:30~3:55 | 이력 캡처: “이 화면은 별도로 이미 승인돼 있던 꽃게 품목입니다. 공급 중단 사유와 원문을 추적할 수 있습니다. 앞선18행을 이번에 승인한 결과로 설명하는 것은 아닙니다.” |

해당 캡처를 README에 표시해 두었으므로 탭4개를 매번 열 필요는 없습니다. 원본 확대가 필요할 때만 이미지를 엽니다. 실제 승인 버튼 시연은 [별도 DB 절차](demo-guide.md)를 완료한 경우에만 이 동선과 교체합니다.

## 3:55~4:40 · 의미 있던 문제 해결 두 가지

“첫째,18행을 읽고도 검토에는8행만 남았습니다. 서로 다른 맛과 가격을 중복으로 합친 로직이 문제였습니다. 병합 셀과 통합 기준을 고쳐 같은 입력의18행을 보존했습니다. 둘째,라벨 하나에서 포장 가격과 개당 가격을 두 품목으로 반환하면서 전체 분석이 멈췄습니다. 라벨은 원재료와 알레르기만 받도록 응답을 줄였고, 오류가 남는 구간은 원문 검수로 넘겨 나머지 처리를 이어가게 했습니다. 실제 실패 작업도 완료 지점부터 재개해 검토본 생성을 확인했습니다.”

README의 두 소제목과 비교 표를 짚습니다. 토큰 수·세부 오류 경로는 질문이 있을 때 [모델 오류 사례](before-after/05-model-schema-recovery.md)를 엽니다. [OCR 수명 관리](before-after/02-ocr-lifecycle.md)·[승인 계약 불일치](before-after/03-review-contract.md)·[삽입 라벨](before-after/04-embedded-labels.md)은 추가 사례입니다.

## 4:40~5:00 · 한계와 다음 단계

“현재는 승인 가능한 초안과 근거 추적까지 구현했습니다. 작은 라벨이나 다양한 업체 양식의 정확도는 더 검증해야 합니다. 다음은 정답셋의 필드 정확도와 실제 담당자의 수정 횟수·검토 시간을 측정하는 것입니다. 자료 정리는 Agent가 하고 확정은 사람이 한다는 경계가 이 프로젝트의 중심입니다.”
