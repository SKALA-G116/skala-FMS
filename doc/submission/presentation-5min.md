## 장면별 화면 내용과 발화

### 1. 식품장부

화면: 업체별 게시글·첨부를 읽고 DB를 직접 정리하는 업무와, 표준 정보·근거를 함께 관리하려는 목표.

대본: “식품장부는 학교급식 공지와 단가표를 식품 관리 데이터로 정리하는 서비스입니다. 업체마다 같은 제품의 이름과 규격을 다르게 쓰고, 품절이나 가격 변경이 이미지와 첨부에 섞여 있습니다. 담당자가 이를 다시 입력하면서 생기는 누락과 근거 추적 문제를 줄이려고 이 주제를 선택했습니다.”

### 2. 시스템 구성

화면: README 아키텍처와 `food-record-v2`의 식품명·업체·규격·알레르기·field_sources.

대본: “사용자는 Vue 화면에서 자료를 등록합니다. FastAPI는 영속 작업을 만들고 worker의 LangGraph가 파싱, 계획, 추출, 품목 연결, Excel 생성을 수행합니다. 텍스트는 일반 파싱하고 이미지는 PaddleOCR로 읽습니다. LLM의 후보를 서버가 검사해 같은 DTO로 보여 줍니다. PostgreSQL은 승인 트랜잭션과 이력을, JSONB는 가변 속성과 추출 결과를 저장합니다.”

### 3. 코드와 기술적 특징

화면: `backend/app/domains/analysis/workflow.py`, `backend/app/domains/review/application.py`의 함수명과 흐름만 크게 보여 준다. 긴 코드를 읽지 않는다.

대본: “핵심은 AI 추출과 DB 반영의 경계입니다. 그래프는 결과를 준비하고, 사용자가 확인·승인한 뒤에 반영 worker가 원문·대상 버전·기간을 다시 검사합니다. 모델은 SQL이나 승인 권한을 갖지 않습니다. MCP는 조회 Tool, 정책·근거 Resource, 작업 Prompt로 구분했고 기본 그래프는 도메인 서비스를 직접 호출합니다. 비동기 HTTP와 OCR 프로세스 재사용으로 다른 작업의 응답과 메모리 사용을 관리합니다.”

### 4. 실제 시연

85초 동선: 완료된 **실제 모델 분석** 열기(10초), 원문·DTO 비교와 한 값 수정(25초), 수정 사유와 품목 확인(15초), 최종 대상 승인·반영(15초), 식품·단가·이력과 원문 링크 확인(20초).

대본: “이 결과는 사전에 이 환경의 실제 모델로 분석한 가상 공지입니다. 원문과 추출값을 비교하고 규격이나 업체를 수정할 수 있습니다. 모르는 값은 공란으로 남기며 알레르기 후보와 함유 표시는 구분합니다. 품목 확인만으로 DB에 반영하지 않습니다. 최종 대상을 승인하면 별도 작업이 반영하고, 식품 상세에서 변경 사유와 원문 근거를 다시 확인할 수 있습니다.”

실제 모델로 완료하지 않은 자료를 실제 모델 결과라고 설명하지 않는다. 라이브 분석이 지연되면 진행 상태를 잠깐 보여 주고, 사전에 성공한 작업의 실행 정보와 결과로 전환한다. 정적 캡처를 쓰면 캡처임을 밝힌다.

### 5. 검증과 개선

화면: PR #1 CI와 `before-after.md`의 제한을 포함한 표.

대본: “백엔드 69개와 프런트 5개 테스트, 배포 빌드가 CI에서 통과했습니다. 승인 전 DB가 바뀌지 않는지, 충돌 시 전체 롤백하는지와 MCP 실행 경계도 확인했습니다. 한 API 파일의 업무 분기를 도메인별로 분리했고 검수 단계를 정리했습니다. OCR 재요청은 한 이미지에서 12.879초에서 10.347초로 줄었지만 예열을 포함한 단일 표본이어서 전체 Agent 개선율로 주장하지 않습니다.”

### 6. 한계와 다음 단계

화면: 정확도 평가, 전체 성능 반복 측정, 대규모 조회·운영 준비 순서.

대본: “현재는 고정된 그래프 안에서 LLM이 계획과 추출을 하는 MVP입니다. 8B 모델은 지연과 메모리 비용이 있고 OCR과 업체별 양식도 사람 검토가 필요합니다. 사용자 승인은 오류 위험을 줄이는 대신 검토 비용을 남깁니다. 다음 단계는 정답 자료로 필드 정확도와 수정 시간을 측정하고, 동일 조건의 성능 비교와 DB 검색·보존 정책을 개선하는 것입니다.”

## 예상 질문

| 질문 | 답변 요지 |
|---|---|
| 왜 NoSQL만 쓰지 않았나? | 승인·기간·관계의 일관성과 가변 속성이 모두 필요해서 PostgreSQL+JSONB 선택 |
| Agent가 전부 자동 처리하나? | 고정 Graph의 계획·추출 자동화이며 사람의 최종 승인과 서버 검증을 유지 |
| MCP를 실제로 쓰나? | stdio 어댑터·전송 테스트가 있고 기본 Graph는 같은 도메인 서비스를 직접 호출 |
| 왜 챗봇이 없나? | 핵심 업무가 원문 검수·장부 관리이므로 우선순위에서 제외 |
| 정확도·시간이 얼마나 좋아졌나? | 전체 정확도/업무 시간은 미측정, 제한된 OCR 관측과 기능 테스트만 설명 |
| 실제 모델 테스트인가? | CI는 테스트 대역, 과거 실제 호출 기록과 발표 환경의 실제 성공 작업을 별도로 제시 |

리허설은 타이머로 2회 진행한다. 설명을 줄일 때도 실제 결과와 테스트 대역의 구분, 승인 경계, 측정 한계를 생략하지 않는다.
