# Before / After와 실측 해석

## 비교 대상을 구분한다

1. 제공된 장애 진단 실습과 신규 식품 서비스의 **기능·목적 비교**
2. 개발 중 단일 API/동기 호출/복잡한 검수 화면과 현재 구현의 **구조·동작 비교**
3. 동일 조건의 입력에 대한 **성능·정확도 비교**

서로 다른 문제의 답변 생성과 식품 추출의 속도를 직접 비교하지 않는다. API 파일의 책임 분리나 줄 수 감소도 처리시간·메모리 절감의 직접 증거가 아니다.

## 이미 확인한 변화

| 검토 UX | 긴 입력 폼에서 품목 선택·원문 대조·최종 반영 단계 | 검수 캡처, reviewJourney 테스트 |

| OCR | 한 프로세스를 재사용하고 유휴 시 해제 | 실제 재사용 기록과 가짜 프로세스 수명 테스트 |

## 기존 실측 원본

출처: `doc/food-agent/ocr-reuse-benchmark.json` 및 `performance-refactor.md`의 2026-10-20 기록.

| 조건 | 시간 | 추출 구간 | 프로세스 |
|---|---:|---:|---|
| 동일 이미지 첫 요청 | 12.879초 | 90 | PID 9873 |
| 같은 프로세스의 재요청 | 10.347초 | 90 | PID 9873 |

차이: 12.879 − 10.347 = **2.532초**. 첫 요청 기준 감소율: 2.532 ÷ 12.879 × 100 = **19.66%**.

이는 한 이미지의 첫 호출과 재호출 비교다. 모델 예열, 파일 캐시, 초기화 효과를 분리하지 않았고 결과 행 수가 같다는 것만으로 OCR 정확도도 같다고 볼 수 없다. 구버전/신버전 전체 Agent의 독립적인 A/B 비교가 아니다.

`performance-baseline.json`과 `performance-after-resume.json`은 같은 장시간 작업을 서로 다른 진행 시점에 기록했다. 각각 완료 구간이 34개와 35개이고 후자는 누적 모델 시간을 포함하므로, 두 숫자를 빼서 전체 처리시간의 개선율을 계산하지 않는다. 후자의 동시 읽기 응답은 개선 후 관측치이며 대응되는 개선 전 측정이 없어 전후 배수 비교를 하지 않는다.

## 보너스 근거를 강화할 후속 측정

- 비교 버전/커밋, 장치·OS·모델·OCR 버전, 파일 SHA-256, 전원/동시 작업 조건을 기록한다.
- cold와 warm 실행을 분리한다. 각 조건을 최소 5회 반복하고 원본값·중앙값·범위를 남긴다. 5회도 예비 표본임을 밝힌다.
- 전체 처리시간 외에 OCR 시간, 모델 호출 수·토큰, 승인 화면 준비 시간, 동시 조회 지연을 별도로 기록한다.
- worker 최대 RSS와 Ollama/OCR 프로세스 메모리를 구분한다. 누적 최고 RSS를 해당 문서만의 메모리로 해석하지 않는다.
- 기대 DTO와 근거를 사람이 작성하고 필드별 정답률·누락·환각·검토 수정 횟수를 함께 비교한다. 속도가 빨라도 품질이 나빠졌다면 트레이드오프로 보고한다.
- 매번 새 시연 DB/원본 revision을 사용해 중복 방지와 checkpoint 재사용 여부를 기록한다. 운영 데이터를 초기화하지 않는다.

## 발표에서 사용할 수 있는 표현

“같은 이미지의 재요청은 첫 요청보다 2.532초 짧았습니다. 단일 표본의 예열 효과를 포함한 관측이며, 전체 Agent의 성능 개선율은 아직 확정하지 않았습니다.”

“비동기화 후 느린 작업 중에도 조회가 진행되는 점은 테스트로 검증했습니다. 모델 자체의 생성 속도가 빨라졌다는 주장은 하지 않습니다.”
