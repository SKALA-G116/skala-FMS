# 식품 DTO 통합 및 아키텍처 점검 — 2026-10-20

## 이번에 적용한 기준

`food-record-v2`를 수집 결과, 검수 입력, 식품 프로필 저장, 식품 조회, 검토 엑셀에서 함께 사용한다. 제조사·브랜드 역할은 공개 DTO에서 없애고 `company_id`, `company_name`이라는 **업체** 하나로 표현한다. 기존 명령·DB의 manufacturer/brand 필드는 이전 데이터 호환용이며 새 화면에서 구분하지 않는다.

- 자료에 없는 값은 `null`. 0원과 미기재는 다르다.
- 식품명은 식별할 이름, 원문 전체 이름은 `raw_food_name`에 보관한다.
- 맛·크기·등급·용도·원산지·원재료는 `attributes`, 낱개 중량·포장 수량·전체 규격·판매 단위는 `specification`으로 분리한다.
- `prices.source_applied`, `survey_1~3`은 원본 가격 열이다. 자동으로 공급 단가 사실을 생성하지 않는다.
- 알레르기는 함유 표시 / 같은 시설·혼입 표시 / 불포함 주장 / 이름·원재료 기반 후보를 구별한다. 공란은 안전·불포함의 의미가 아니다. 자료 검토 완료와 알레르기 표시 검토 완료도 별개다.
- `field_sources`와 변경안의 `field_evidence`, 감사 이력으로 원문·시트·셀/본문 구간·OCR 영역과 검토자를 추적한다.

예: `CJ씨푸드 맛있는빅후랑크(오리지날_100g*10입 1Kg/EA)` → 업체 CJ씨푸드 / 식품명 맛있는빅후랑크 / 맛 오리지날 / 낱개 100g / 10입 / 전체 1kg / 판매 EA. 인식되지 않는 명칭은 무리하게 자르지 않고 원문을 유지한다.

## 실제 처리 경로

1. 수집기가 게시글과 이미지·첨부 원본을 버전 및 해시와 함께 확보한다.
2. 일반 텍스트는 직접 읽고, 이미지·스캔 PDF는 PaddleOCR로 텍스트와 영역을 얻는다.
3. 알려진 헤더의 Excel·CSV·탭/파이프 구분 텍스트·HTML 표는 열 매핑으로 동일 DTO를 구성한다. 알려진 표 열을 다시 LLM으로 추측하지 않는다.
4. 비정형 본문, OCR 조각, 모르는 표 양식은 로컬 LLM이 근거 구간을 지정해 식품/변경 사실을 추출한다. 호스트가 스키마·금액·적용일·규격 및 인용을 검사하고 공통 DTO에 넣는다. 식품 소개도 `food_profile`로 다룬다.
5. 검수 화면은 입력 종류와 관계없이 같은 열의 표를 먼저 표시한다. 선택한 행을 원문과 나란히 비교하고 수정·확인·제외한다.
6. 확인한 행의 명시적 승인·반영 요청이 기존 변경안 검증·승인·작업 큐를 호출한다. 식품 프로필·기간별 단가/공급 상태·감사 기록은 하나의 DB 트랜잭션으로 반영한다.
7. 식품 목록은 동일 DTO를 읽는다. 다운로드는 표준 식품 정보 시트와 원문 근거·변경 사실 시트를 포함한다. 과거 추출 결과의 다운로드도 새 양식으로 생성할 수 있다.

## DB 판단

지금은 DB 종류를 바꾸기보다 표준 DTO와 쓰기 경계를 일치시키는 것이 우선이다. 유동적인 속성은 PostgreSQL JSONB 문서로 보관하고, 단가의 적용 기간·중복 반영 방지·승인 버전·이력은 트랜잭션으로 묶는다. MongoDB 역시 스키마 검증과 트랜잭션을 지원하므로, NoSQL이라서 검수가 단순해지거나 스키마가 없어지는 것은 아니다.

근거: [PostgreSQL JSON 타입](https://www.postgresql.org/docs/17/datatype-json.html), [MongoDB 스키마 검증](https://www.mongodb.com/docs/manual/core/schema-validation/), [MongoDB 트랜잭션](https://www.mongodb.com/docs/manual/core/transactions/).

## 검증

독립 테스트 DB에서 DTO 변환, 텍스트/표 계약 일치, 결측·0원, 업체 통합, 알레르기 표시 구분, 중복 근거 병합, 검수 수정·승인·저장·조회·출력과 기존 회귀 경로를 검증한다. 실제 모델 검증과 테스트 대역 기반 통합 검증은 별도로 기록한다. 실제 자료의 DB 반영은 사용자의 행 검수·승인을 거친다.

## 삭제·복구 및 화면 개선 추가

식품(`DELETE /foods/{variant_id}`)과 업로드·수집 자료(`DELETE /documents/{id}`) 모두 목록에서 삭제하고 `POST .../{id}/restore`로 복구한다. 본문의 `archive_version`, CSRF, 요청 식별 키, 담당자 권한을 검사한다. 식품 삭제는 식품 및 단가 목록에서 숨기며 자료 삭제는 자료함과 연결된 원본 엑셀 목록에서 숨긴다. 이미 반영된 식품 정보, 원본 파일, 근거, 기간별 사실은 지우지 않는다. 삭제/복구의 주체·사유·전후 상태는 감사 기록에 남는다.

- 식품 쓰기와 삭제는 동일한 DB 잠금으로 직렬화하며 대상 버전을 올린다. 삭제된 식품에 새 변경안을 반영하려면 복구가 필요하다.
- 분석 대기·실행 중인 자료 삭제는 충돌 응답으로 막는다. 삭제된 자료는 수집 시 자동 분석과 수동 재시도를 건너뛰거나 차단한다.
- ‘삭제한 식품’, ‘삭제한 자료’ 탭 및 직전 작업 실행 취소를 제공한다.
- 대시보드, 메뉴, 자료함, 파일 가져오기, 식품 표와 상세 패널을 재구성했다. 글자 크기·대비를 높였으며 검수 화면의 중복 품목 목록을 제거했다.
- 일반 삭제는 복구 가능하며, 삭제한 자료의 영구 삭제는 아래 경로로 별도 제공한다.

## 전체 선택·일괄 처리·영구 삭제

- 행별 체크박스, 현재 페이지 전체 선택, 검색 결과 전체 선택(다른 페이지 포함), 선택 해제를 제공한다. 선택 당시 자료 ID와 삭제 버전을 묶어 보내므로 변경된 항목을 무시하고 삭제하지 않는다.
- `GET /document-selections?q=...&archived=true|false`가 조건에 맞는 선택 목록을 반환한다. 현재 개발 상한은 2,000개이며 초과하면 명시적 오류를 반환한다.
- `POST /document-actions`는 `action=archive|restore|purge`, `items=[{id,archive_version}]`를 받는다. 영구 삭제에는 `confirmation="영구 삭제"`가 필요하다. 서버는 사용자 권한·CSRF·요청 식별 키를 검사하며 항목별 성공/실패와 사유를 반환한다.
- 영구 삭제는 삭제한 자료만 대상으로 한다. 원문 버전·첨부 자산 메타데이터·추출·근거·분석 결과·검토 스냅샷·미승인 변경안·원본 표 행·분석 작업·LangGraph 체크포인트·응답 캐시를 정리한다.
- 승인·반영된 식품이나 감사 이력에서 인용하는 근거, 승인된 변경안과 연결된 자료, 다른 자료와 함께 작성한 변경안은 보호하고 이유를 표시한다.
- 삭제 후 원본 파일 정리는 커밋 이후 실행한다. 동일 해시 파일을 다른 자산이 사용하면 보관한다. 파일 쓰기와 정리는 같은 잠금을 사용하고 실패한 정리는 재시도 큐에 남긴다.
- 사이트 자료는 최소 게시글 식별자를 재수집 제외 목록에 남겨 다음 수집 때 되살아나지 않게 한다. 자료 본문은 남기지 않는다. 영구 삭제 자체의 사용자·시각·사유는 최소 감사 기록으로 남긴다.
- 삭제 테스트는 실제 파일 저장소와 분리된 임시 폴더 및 별도 테스트 DB에서 실행한다.
