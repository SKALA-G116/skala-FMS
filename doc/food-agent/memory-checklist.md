# 메모리·자원·복구 사전 검토 — v0.2

## 1. 검토 결과를 읽는 방법

기존 원본 코드는 실습용이며 신규 서비스는 아직 구현하지 않았다. 따라서 ‘설계 반영’은 문서·계약에 통제를 명시했다는 뜻이다. 메모리 누수 없음, OCR 처리 성능 확보, 장애 복구 통과를 의미하지 않는다. 구현 후 검증 항목은 모두 미실행이다.

검토에서 발견한 주요 빈틈:

1. v0.1에서 생략 가능했던 MCP에 기능별 계약과 모델 허용 목록이 없었다. → 6종 Tool/5종 Resource/3종 Prompt, 호출 주체와 권한을 추가했다.
2. 작업 테이블만으로 그래프 중간 단계 복구가 보장되는 것처럼 해석될 여지가 있었다. → PostgreSQL checkpointer·factory·run/thread 분리와 재개 규칙을 명시했다.
3. ‘페이지별 처리·동시성 제한’의 실제 상한과 초과 동작이 없었다. → 조정 가능한 초기 예산과 중단/부분 결과 규칙을 runtime-policy에 추가했다.
4. Resource·Tool·checkpoint에 대형 원문이 복제될 위험이 있었다. → 고정 segment 참조, 반환/상태 크기 제한, 버전 포함 캐시 키를 추가했다.
5. 문서 상세와 제품 상세 응답이 커질 가능성이 있었다. → 본문 미리보기와 목록 페이지 제한·프런트 이미지 해제 기준을 보강했다.
6. 같은 checkpoint를 두 작업자가 복구할 때의 실행 소유권이 불명확했다. → run lease·단조 증가 fencing token과 반영 전 소유권 검사를 추가했다.

## 2. 서로 다른 다섯 종류의 메모리

| 종류 | 저장할 내용 | 위치·규칙 |
|---|---|---|
| LLM 작업 문맥 | 해당 segment·머리글·관련 규칙·후보 일부 | 토큰 예산 안에서만 조립. 모든 과거 문서·대화 미주입 |
| 실행 체크포인트 | 현재 단계·run ID·고정 입력·산출물 ID·cursor | PostgreSQL, 실행별 namespace, 작은 상태 |
| 업무 장기 기록 | 제품·가격·상태·승인·정정·근거 | 관계형 DB. 요약·벡터 검색 결과로 대체하지 않음 |
| 원본·파생 파일 | 이미지·엑셀·OCR 구조·표 조각 | 파일 저장소와 DB 메타데이터. 전부 RAM에 적재하지 않음 |
| 프로세스 RAM/VRAM | OCR 모델·페이지 버퍼·연결·캐시 | 역할별 프로세스, 재사용, bounded concurrency·캐시 |

‘메모리를 위해 벡터 DB 추가’는 이번 요구를 해결하지 못한다. 업무 이력의 정확한 시점 조회와 중복 반영 방지는 SQL·트랜잭션의 책임이다. 대화 요약도 원문·가격·제품 식별의 정답 저장소로 쓰지 않는다.

## 3. RAM 예산을 잡는 방식

대략적인 배포 메모리는 다음 항목의 합으로 계산하고 실제 RSS/VRAM을 측정한다.

```text
전체 RAM ≈ API 프로세스 수 × API 기본 메모리
         + 분석 호스트 수 × (그래프·클라이언트·MCP 자식·제한 캐시)
         + OCR 작업자 수 × (OCR/표 모델 + 동시 페이지 작업 메모리)
         + 로컬 LLM 런타임(사용 시)
         + PostgreSQL·파일 버퍼·운영 여유
```

페이지 작업 메모리는 압축 파일 크기가 아니라 decoded width×height×channels와 전처리 복사본·추론 tensor의 영향을 받는다. base64는 대략 원본 바이트의 4/3이고 JSON/문자열/복사본은 추가 비용이다. 따라서 ‘첨부 20MiB 이하’만으로 메모리를 제한했다고 볼 수 없다.

프로세스당 한 번 생성은 전체 배포에서 한 개라는 뜻이 아니다. Uvicorn worker 4개에 OCR을 각각 로딩하면 4개 모델이 생긴다. v0.2는 API에 OCR을 로딩하지 않고 OCR 작업자 1개부터 시작한다. 로컬 LLM을 사용하면 그 모델 메모리도 OCR과 함께 예산에 넣는다. 서버 사양 미확정이므로 필요한 GB나 GPU 사용 여부를 보장하지 않는다.

## 4. 초기 상한과 초과 동작

[runtime-policy.json](./runtime-policy.json)의 값은 안전한 시작을 위한 조정 가능한 정책 초안이다. 성능 측정 결과나 운영 SLA가 아니다.

| 대상 | 초기 정책 | 초과 시 |
|---|---|---|
| 업로드 | 파일 20MiB | 413, 분할/지원 범위 안내 |
| 문서 | 20페이지, 이미지 16MP, 엑셀 2만 행/20만 비어 있지 않은 셀 | 분석 거절 또는 명시적 분할 작업. 조용히 자르지 않음 |
| OCR | 작업자 1개, 한 작업자당 1페이지 작업 | 큐 대기, worker 수는 메모리 측정 후 증가 |
| 네트워크/LLM | source당 네트워크 1개, 호스트당 LLM 2개 | semaphore와 backpressure |
| Tool/Resource | 텍스트 결과·segment 각각 32KiB | 더 작은 segment·검색 범위 또는 명시적 오류 |
| 체크포인트 | 직렬화 state 256KiB | 대형 값을 artifact로 이동 후 ID만 저장. 불가하면 실패 |
| 호스트 캐시 | 메타데이터 중심 128MiB byte-LRU | 오래된 캐시 제거, 새 결과는 영속 저장소 참조 |
| LLM | 호출당 입력 최대 12k/output 4k 토큰, reserve 2,048 | 실제 모델 window에 맞춰 더 낮춤. 작동 불가능하면 분할/실패 |
| 분석 전체 | 입력 120k/output 32k 토큰, 600초 | partial/blocked/failed와 남은 범위 표시 |
| 반복 | 보완 1회, 의미 검토 최대 2회, transport 최대 총 3회 | 강제 합격 없음. 의미 오류를 transport 재시도로 숨기지 않음 |
| 완료 checkpoint | 완료 후 14일 기본 정리 | 활성 run·승인 근거와 별도. 사업 보존 정책 확정 필요 |

모든 이미지 모델에는 실제 사용 버전의 입력 조건도 적용한다. 처음부터 긴 이미지 전체를 축소해 작은 글자를 잃지 않도록 원본 보존과 영역 분할을 사용한다. 표 분할은 머리글·각주·전역 적용일을 각 segment와 연결한다.

## 5. 재시작·복구·lease

analysis_run_id는 원문 revision과 처리 버전에 연결한다. checkpoint thread는 서버가 `analysis:{run_id}`처럼 namespace를 붙인다. 사용자 ID나 원문 게시글 ID 하나를 모든 실행의 thread로 공유하지 않는다.

- 일시적 실패 후 같은 입력·같은 코드/파서/프롬프트/정책 버전의 retry는 같은 run을 복구할 수 있다.
- 새로운 원문·새 모델/정책·force_reprocess는 새 run/thread다. 중간 결과를 섞지 않는다.
- job ID는 시도별 실행 기록이며 run ID와 구별한다. API의 Job.analysis_run_id로 연결한다.
- 한 run에는 동시에 하나의 유효 lease만 허용한다. lease 획득 때 fencing token을 증가시킨다.
- heartbeat·lease 연장 실패 시 작업자는 쓰기·checkpoint 진행을 멈춘다. 산출물·변경안 쓰기 직전에 token과 소유권을 확인한다.
- 외부 호출·artifact 저장은 재실행될 수 있다. 입력 hash·단계 키·run 범위의 고유 제약으로 중복을 막는다.
- checkpoint와 업무 반영 DB 트랜잭션은 별개다. 반영은 application 고유키와 원자적 이력 기록으로 한 번만 실행한다.
- PostgreSQL 장애 시 MemorySaver로 조용히 fallback하지 않는다. 신규 분석을 일시 중단하고 API에 상태를 알린다.

AsyncPostgresSaver 생성·연결·정리는 factory에서 수행한다. migration/setup은 배포 초기화에서 수행하고 요청마다 DDL을 실행하지 않는다. 호환되는 psycopg async pool은 같은 프로세스 안에서 공유할 수 있지만 API·MCP 자식·OCR·스케줄러는 서로 다른 프로세스이므로 실제 연결 수를 합산한다. PostgreSQL 연결 객체 하나를 모든 동시 요청이 공유하는 설계는 피한다.

## 7. 구현 후 확인할 실험

1. 동일한 이미지/표/엑셀 표본을 반복 처리하고 idle 후 RSS·VRAM·열린 파일·DB 연결·MCP 자식 수가 안정되는지 확인한다. `gc.collect()` 호출 자체를 통과 조건으로 삼지 않는다.
2. OCR 중 API 조회·승인 응답이 같이 지연되는지 확인한다. 별도 프로세스라도 CPU/RAM 경합이 생길 수 있으므로 실제 자원 제한을 측정한다.
3. worker를 추출·제안 저장·checkpoint 직후 중단하고 재개해 이미 만든 산출물과 제안이 중복되지 않는지 확인한다.
4. lease 만료 후 새 worker가 재개한 상태에서 이전 worker가 늦게 돌아오게 해 오래된 token의 쓰기를 차단한다.
5. 16MP 초과 이미지, 지나치게 많은 엑셀 셀, 긴 표, 손상·압축 폭탄·암호 파일, 오래 걸리는 파서에서 예산과 종료가 작동하는지 확인한다.
6. Vue에서 여러 원문을 연속 열고 닫아 canvas·Blob URL·이벤트·polling·검색 cache가 계속 쌓이지 않는지 확인한다.

## 8. 아직 미정인 항목

배포 RAM/VRAM과 OCR 프로세스 메모리 한도, DB 총 연결 예산, 실제 사용할 LLM context window, 실제 문서의 처리 시간, 승인 근거 보존 기간은 미정이다. 이 값들이 채워지고 실험을 통과하기 전에는 자원 효율이나 안정성을 검증 완료라고 보고하지 않는다.
