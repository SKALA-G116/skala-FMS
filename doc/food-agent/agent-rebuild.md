# Agent 판단 중심 리빌드 명세

작성자: 김재현(Finn) · penguin.klg@gmail.com · 2026-10-21. 라이선스: 미지정.

## 문제와 결과

이전 계획의 tasks는 실행을 거의 제어하지 못했고, 대부분의 자료를 동일한 작은 텍스트 구간으로 해석했다. 첫 네 구간을 모든 상품의 문맥으로 재사용하고 일부 결과를 같은 모델로 다시 생성했다. 추출 직후에는 검토 전부터 내부 연산 묶음의 변경안이 생성됐다.

이제 Agent가 자료별 tool과 reason을 반환하고 실행기가 해당 도구만 실행한다. 정규화할 표를 다시 전부 LLM에 넣지 않으며, DB 후보 조회도 계획에서 선택한 경우에만 실행한다. 추출은 한 검토본을 만들고, 사용자 확인 후에만 승인용 변경안을 만든다.

## 기능 경계

| 기능 | 코드 | 책임 |
|---|---|---|
| 자료 관찰 | `analysis/workflow.py:extract`, parsers | 텍스트·표·OCR을 읽고 근거 ID·좌표·셀 보존 |
| Agent 판단 | `analysis/planning.py:decide` | 내용 샘플·열 인식 상태·사용 가능한 도구를 보고 자료별 처리 결정 |
| 선택한 도구 실행 | `analysis/agent.py:interpret` | 계획 검증 후 표 매핑·의미 추출·상품 영역 판단·원문 확인 요청 실행 |
| 공통 Output DTO | `catalog/record.py` | nullable 식품 정보·규격·원재료·알레르기·가격의 단일 계약 |
| 중복 통합 | `analysis/consolidation.py` | 업체·규격·코드·기간별 근거 통합 |
| DB 후보 조회 | `analysis/matching.py` | Agent가 선택하면 식품별 제한된 읽기 쿼리 실행, 승인·생성 없음 |
| 검토와 변경안 준비 | `review/items.py`, `review/staging.py` | 확인한 DTO만 변경안으로 만들기 |
| 승인·DB 반영 | `review/proposals.py`, `review/application.py` | 권한·버전·기간·근거 검증 후 원자적 반영·이력 |

LangGraph: `extract → plan → execute_tools → [match 또는 생략] → export`. checkpoint에는 ID만 전달한다. 업무 반영은 별도 검토·승인 흐름이다.

## Agent가 선택하는 도구

| 도구 | 입력 판단 | 실행 |
|---|---|---|
| normalize_table | 인식한 표의 열이 충분함 | 파싱된 행을 DTO로 정규화. 남는 본문은 수동 확인으로 보존 |
| extract_text | 비정형 본문·표를 의미적으로 해석해야 함 | 해당 자료의 텍스트만 LLM으로 추출 |
| extract_image_regions | OCR의 상품별 배치와 공통 범례 연결이 필요함 | 좌표와 텍스트로 상품 영역 판단 후 영역별 LLM 추출 |
| request_review | 자동 처리를 신뢰하기 어려움 | 추측 없이 원문 확인 요청. 추가 추론·DB 조회·변경안 생성 생략 |

자료 ID의 중복·누락, 사용할 수 없는 도구, 이미지 줄의 누락·중복, 초과 입력은 명시적인 오류로 처리한다. 임의 SQL·코드 실행·자동 승인을 Agent에게 제공하지 않는다. 모델 응답을 신뢰하고 DB를 바로 고치지 않는다.

이미지의 source_ids는 상품 고유 근거이며, context_ids는 해당 상품에 필요한 제목·업체·기간·범례다. 첫 네 줄을 무조건 다른 상품에 붙이는 경로와 동일 모델의 전수 재검증 호출을 제거했다. 상품 영역은 문자 수 기준으로 중간에서 자르지 않는다. 아직 분류하지 못한 줄은 별도 근거와 경고·Excel에 보존하고 완료 구간 수에서 제외한다.

## 메모리·재개

- 전체 원문 대신 자료별 제한된 샘플·열 인식 결과로 도구를 판단한다.
- LangGraph는 ID 위주 상태를 유지한다. 실행 구간 재개에는 근거 ID·문자 범위만 보관하여 원문 전체를 복사하지 않는다.
- 완료한 도구와 이미지 영역 판단을 저장하여 재개 시 반복 호출하지 않는다.
- LLM/OCR 동시성 제한·입력/출력/실행 예산·취소·lease 검사는 유지한다.
- DB 후보 조회는 필요한 식품명·공통식품코드별 LIMIT 쿼리와 실행 내 재사용을 적용한다.
- 표 작업 화면은 미리보기 5개만 렌더링하고 전체 검토 화면으로 한 번만 이동한다. 미분류 원문은 10개씩 읽는다.

## Tool / Resource / Prompt

실행 도구 선택은 `planning.TOOLS`가 정의한 제한된 계약이다. 내부 실행은 같은 프로세스의 도메인 함수를 호출하며 도구마다 별도 MCP 프로세스를 띄우지 않는다.

MCP Tool은 기존 후보·사실·이력 조회와 `get_agent_execution`을 제공한다. `food://agent/tools` Resource는 도구 명세를 읽기 전용으로 제공한다. 스키마·정책·근거 Resource와 공지·단가표·검토 Prompt를 유지한다. 승인과 최종 DB 반영은 권한 있는 HTTP 업무 API의 책임이다.

## 제거한 레거시

사용하지 않는 장애 진단 원본 `legacy/incident_agent/`와 `backend/app/{ai,food,domain,services,workflows,workers}`, `backend/app/db.py` 호환 진입점을 제거했다. 원본과 변경 이력은 Git에 남는다. 현재 실행·문서·테스트는 도메인 경로만 사용한다. 명시 형식의 rules 경로는 자동 테스트 대역으로 남기며 운영 기본값은 Agent다.

## 검증 범위와 한계

단위·통합 테스트는 도구 선택의 실제 실행, 표 매핑, 상품 영역별 근거 분리, 원문 누락/중복 차단, 경량 재개 참조, 중단·재개·취소, 검토 후 반영, MCP 권한 경계를 검증한다. 실제 모델 추론과 TestModel/HTTP mock 결과를 구분한다.

현재 모델은 텍스트 모델이다. 원본 이미지를 직접 보는 시각 모델이 아니므로 최초 OCR로 관찰한 뒤 그 좌표와 텍스트로 상품 영역을 구분한다. 상품 crop의 고해상도 재인식, 복잡한 이미지 표의 정확도 전체 검증, 모든 업체 양식의 추출 정확도를 보장하는 단계까지 완료한 것은 아니다. 입력 예산을 넘는 이미지 페이지는 임의로 잘라 처리하지 않고 원문 분할을 요청한다.

새 변경안 생성 경로를 바꿔도 이전 분석·검토·승인 기록은 삭제하거나 덮어쓰지 않는다. 이전 완료 결과는 최신 Agent 실행으로 재분석하거나 원본 표만 재정리할 수 있다.


## 경량 모델 실측과 적용

2026-10-21 이 개발 환경에서 동일한 실제 두 시트 단가표의 도구 선택을 비교했다. 아래는 제한된 사례의 wall time이며 모델 로딩·캐시 조건을 통제한 일반 성능 벤치마크가 아니다.

| 모델 | 도구 선택 시간 | 판단 결과 | 적용 |
|---|---:|---|---|
| Qwen2.5 0.5B | 5.56초 | 동일 표의 한 시트를 extract_text로 잘못 선택 | 기본값에서 제외 |
| Qwen3 1.7B | 8.82초 | 한 시트를 extract_text로 선택, 세부 추출에서도 오류 | 기본값에서 제외 |
| Qwen3 4B | 4.38초 | 두 시트 모두 normalize_table 선택 | Agent 도구 선택용 |
| Qwen3 8B | 15.13초 | 두 시트 모두 normalize_table 선택 | 비정형 추출용 유지 |

운영 프롬프트로 추가한 두 가지 추출 시험에서 4B는 원재료 문구와 일시중단 종류를 일부 추출했지만 금액·날짜·업체 오류가 남았다. 8B는 해당 두 시험의 기대 항목을 통과했다. 따라서 경량화는 판단 단계부터 적용하고 모든 추출을 작은 모델로 강제하지 않는다. 4B의 문서 분류 라벨은 단가표를 marketing으로 잘못 표시했지만 실제 실행은 도구 선택 routes를 기준으로 하며 두 자료 모두 표 도구로 처리됐다. 이 분류 정확도도 향후 평가 대상이다.

설정: `FOOD_PLANNER_MODEL_NAME=qwen3:4b`, `FOOD_EXTRACTION_MODEL_NAME=qwen3:8b`. 기존 `FOOD_MODEL_NAME`은 명시적 역할 설정이 없을 때의 기본값으로 유지한다. 모델이 다르면 planner는 `keep_alive=0`, context 8192로 설정하여 판단 후 내려가도록 하고, 실제 의미 추출이 필요한 경우에만 extraction 모델을 사용한다. 표 정리에는 8B를 호출하지 않는다. 두 모델의 실제 요청·토큰·소요 시간은 보고서에 남는다.

공식 배포 정보: [Qwen3 4B](https://ollama.com/library/qwen3:4b), [Qwen3 1.7B](https://ollama.com/library/qwen3:1.7b). 다운로드 크기는 실행 중 RAM/VRAM 사용량과 다르다.

재현: `python scripts/evaluate-agent-model.py --run-id <기존 완료 분석 ID> --model qwen3:4b`. 운영 추출과 같은 payload·프롬프트·스키마로 시험하며 DB 확정 정보나 사용자 검토 결정은 수정하지 않는다. 기본 결과 파일은 Git에서 제외된 `.local/`에 저장한다.


## 실제 전체 실행 확인

새 작업자로 기존 520개 원문 구간을 처리해 **259개 검토 품목**, **모델 호출 1회(Qwen3 4B, 9.729초)**, 검토 전 변경안 **0개**를 확인했다. 두 시트 모두 Agent가 normalize_table을 선택했고 8B 추출은 실행하지 않았다. 작업 등록부터 완료까지 약 11.7초(큐 대기·Excel 생성 포함), worker 최고 RSS는 약 189.9MiB였다. 이 RSS에는 별도 Ollama·PaddleOCR 프로세스 메모리가 포함되지 않는다. 전체 메모리 개선율이나 이미지 처리 성능을 입증한 수치가 아니다.

간장 원재료 생멸치 75%(국산), 천일염 25%, 기타 속성 2년숙성을 실제 검토 화면에서 원문과 대조했다. 기존 승인 DB는 변경하지 않았다. Backend 97개, Frontend 동선 5개 테스트 및 Frontend 빌드·파일 명세 검사를 통과했다.
