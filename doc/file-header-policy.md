# 파일 명세·변경 이력 작성 규칙

예시 형식을 적용하되 작성자·이메일·라이선스는 모두 **미지정**으로 둡니다. 예시의 인물·이메일·Proprietary를 복사하거나 과거 원저자에게 새 이름을 부여하지 않습니다.

## 파일 안에서 확인하는 내용

- 파일명·역할, 입력·출력 계약, 실행 가정, 작성 정보, Revision History
- Python은 모듈 docstring과 `__author__`, `__email__`, `__version__`, `__status__`를 제공합니다.
- Profile·DTO·실행 함수는 해당 파일에 실제로 있는 계약을 설명합니다. 웹/API·마이그레이션 파일에 가짜 LDAProfile이나 Recipes 구조를 만들지 않습니다.
- 작성일은 최초 Git 등록일입니다. 원본 작성일이 확인된다는 뜻이 아닙니다. 최초 명세 버전 0.1.0은 현재 프로젝트의 문서 baseline이며 API/DTO의 스키마 버전과 구분합니다.
- `legacy/`는 제공 원본이므로 직접 헤더를 쓰지 않습니다. 파일 목록에서 같은 작성 정보·역할·이력을 확인합니다.

## 형식을 보존하는 파일

실제 모델에 전달되는 MCP Prompt·정책은 토큰과 의미를 보존하도록 외부 명세로 관리합니다. JSON에는 주석이나 임의 metadata 필드를 추가하지 않습니다. CSV·가상 TXT 입력·생성 lock 파일·이미지에도 헤더를 삽입하지 않습니다. 모든 추적 파일은 `doc/file-manifest.json`에 입력·출력·가정·기록을 제공하고 `doc/file-specs.md`에서 찾아갈 수 있습니다. 두 생성 목록 자체는 순환 hash를 피하기 위해 self-hash를 두지 않습니다.

## 변경할 때

1. 실제 코드를 수정하고 필요한 함수·클래스 docstring/DTO 필드 설명을 함께 수정합니다.
2. 파일 헤더의 Revision History에 실제 변경일, 확인된 작성자(미확인이면 미지정), 버전과 변경 이유를 추가합니다. 과거 날짜나 하지 않은 성능 검증을 만들지 않습니다.
3. 새 파일은 `python3 scripts/file-specs.py --apply`로 누락 헤더를 생성합니다. 이 명령은 이미 있는 헤더를 덮어쓰지 않습니다.
4. `python3 scripts/file-specs.py --refresh`로 목록·Git snapshot·현재 hash를 갱신합니다. 이후 `--check`와 해당 기능 테스트를 실행합니다.
5. 소스와 목록을 같은 커밋으로 저장합니다. 이후 최신 이력은 `git log --follow -- <파일>` 또는 GitHub History/Blame으로 조회합니다.

`git_history`는 목록 생성 시점의 실제 commit/date/subject이며 그 이후 커밋을 예측하지 않습니다. 파일 상단의 명세 추가 기록은 이번 작업 기록이고, 프로젝트 전체의 세부 변경 이력을 대신하지 않습니다.

셸 shebang·Python future import·Vue SFC·SQL·YAML 문법을 보존합니다. 파일 위치가 바뀌거나 라이선스/담당자가 확정되면 정책과 검사 도구를 함께 갱신합니다.
